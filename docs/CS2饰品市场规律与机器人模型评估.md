## §1 一句话结论（修正）

**工程口径很讲究，市场标定有硬伤，有效性尚未被证明。**

- **合理**：数据诚实（不伪造成交量）、`售价/求购价>3.0` 判死盘实测精准（池内 p50=1.070、p95=1.318、>3.0 占 **0%**）、缺失不填 0 + 置信度折扣、高价品单独降噪、T+7 视角与推送冷却。
- **硬伤**：五维评分里 **`order_ratio` 退化且方向反了**、**`spread` 方向盲**；模型里**没有手续费 / 提现费 / 7 天冷却 / 跨平台价差**（而跨平台价差的数据源其实拿得到）；`min_price` 一道闸承担 69%~82% 的过滤量，说明**整个筛选体系的杠杆点只有一个，且是拍出来的**。
- **有效性**：评分在 **+24h 有弱正向横截面排序能力（IC≈+0.12，不显著）**，到 **+7d 衰减为 0**；而推送文案最强推的周期形态（建仓/启动）在**同一价格带内**跑输"无形态"事件——这是本报告最值得警惕的一条。

## §2 CS2 饰品市场的真实运作规律（对照基准）

| 机制 | 现实情况 | 机器人的处理 |
|---|---|---|
| **价格发现** | 平台展示的"最低在售价"是**要价**；成交发生在要价与最高求购价之间。只有 Steam 有公开成交记录。 | 用 BUFF 最低在售价当"价格"。**没有把要价与成交价区分开**（PRD 只在"量"上守边界，价上没守）。 |
| **两条通道** | Steam（全球池、钱包闭环、约 15% 费率、不可提现）+ 国内平台（BUFF/悠悠/C5/IGXE/ECO，人民币、可提现、卖家费约 2%~3.5%、提现约 1%）。**跨平台价差是"倒货"利润主来源**。 | 有 `yyyp_sell_price`/`steam_sell_price` 字段（`client.py:186-188`）但**只落 BUFF 价**；未做跨平台价差（Steam 价为美元，还需汇率口径）。 |
| **7 天冷却** | 交易/购买后 7 天内不可再交易、不可上架。T+7 是硬约束。 | 文案层有"T+7 视角"，代码层无冷却字段。 |
| **供给** | 开箱注入 + Steam 库存回流 + 封禁/回收；版本/赛事/主播/情绪驱动需求。 | `sell_num` 当外生常数；"在售+10%"无法区分出货与开箱放量。 |
| **盘口结构** | **在售数天然远大于求购数**（本库实测中位 **0.080**，p90=0.25）。 | 见 §3.1：中性点取 1.0，方向还反了。 |
| **交易成本** | 单边费 2%~3.5% + 价差（实测中位 **7%**）→ 往返成本约 4%~10%。 | `launch` 只要"1h 跟涨 ≥1%"即确认启动；`liquid` 用"价差 ≤3%"过滤（低于市场中位）。 |

## §3 逐条合理性审查

### 3.1 `order_ratio`（权重 5）：退化 + 方向反了

`engine.py:259-270`：`dev=|ratio-1.0|`，`dev≥1.0` 满分。实测 1149 个在池饰品：

```
求购/在售比  p5=0.023  p25=0.048  p50=0.080  p75=0.138  p90=0.250  p95=0.351
ratio≥1.0 = 0.4%      ratio≥1.5 = 0.0%（"需求偏强"分支是死代码）
该维度得分区间仅 3.24 ~ 4.89（中位 4.60）
```

两点后果：
1. **不是"没信息"，而是"方向反了"**：得分最高的是 `ratio≥2`（需求碾压，几乎不存在）或 `ratio=0`（死盘，已被 `min_buy_num` 拦掉）；而**真正求购≈在售的品（ratio→1）拿 0 分**。唯一接近"需求真旺"的形态被判为"不异常"。
2. 这 5 分近似常数 → L2=55 分实际等于其余四维 50.4 分，**阈值与分数绑在一起被整体抬高**，改这一维必须同步重标定阈值。

另：`ratio ≤ 0.3` 会追加"供应偏多"表述（p90=0.25 → 池内超 90% 的品都会命中；实测事件文案覆盖率 55.4%，差额来自 `buy_num_observed=False` 的沿用值与 139 条旧版事件无文案）。**把一个常态结构当异常特征播报**。

### 3.2 `spread`（权重 15）：方向盲 + 百分比之百分比

`engine.py:290` 取绝对值打分 → "价差扩大"与"价差收窄"同分。实测事件文案中价差项覆盖 19.9%（收窄 10.7% + 扩大 9.2%），且全场最高分事件（**87.6 分 / L4 / ¥16,976**）的驱动之一就是"买卖价差扩大 30%"——对买方是**恶化**信号，却拿到满分并推 L4。

`engine.py:280-286` 兜底路径算的是"价差的百分比变化"，低价品上出现 **"买卖价差收窄 340%"** 并进 L3（83.8 分 / ¥9）：¥9 品的价差从 1% 变到 4.4% 只有 3 毛钱。

### 3.3 低价带：不是"噪声"，是"成本与颗粒度不匹配"

v1 我写"低价=百分比噪声"，**价格分层回测不支持这个说法**（¥<50 -7.93%、¥50-300 -8.98%、¥300-5000 -7.86%，无差异）。成立的是另外三条：

1. **成本占比**：¥20 的品涨 10% 是 ¥2；扣掉单边费 2%~3.5%、提现 1%（且有最低额）、7 天锁定，**没有可操作的边际**。而百分比阈值让 ¥5-50 的品触发频率是高价品的数倍 → 推送结构自然倾斜：雷达事件价格 **p25=¥12、p50=¥40、<¥50 占 52%、<¥10 占 22%**。
2. **绝对变动没有下限**：引擎对**盘口数量**做了三重判定（`book_abs_low/mid/high`：低基线 ≥3 单、中 ≥5、高 ≥15），但对**价格**只有百分比、没有绝对金额下限。这是一个明确的不对称：**量的噪声防住了，价的噪声没防**。→ 修法应是"百分比 + 绝对金额"双阈值，而不是按价格带一刀切。
3. **引擎自己的文案已承认异常**：事件 `78.9 L3 surge ¥21,000` 的 reason 里写着"求购 +100% 但绝对仅 +2 单，噪声不计"，仍然以 L3 推送。原因是 `engine.py:585` 的 `min_anomaly_buy_num` 只在 `buy_num_observed=True` 时生效，批量查价缺字段的那一轮沿用历史值即跳过该门槛，叠加 60 分钟观察期 → **求购深度这道线存在旁路**。

### 3.4 闸门体系：真实约束与"保险丝"（v1 此节结论错误，已重写）

来自 2,622 行"评分分布"日志的**累计拦截量**（不是池内命中率，避免循环论证）：

```
A 池 1,791 轮  拦截合计 672,659         B 池 831 轮  拦截合计 689,990
  min_price            462,090  68.7%      min_price            567,366  82.2%
  min_sell_num          83,303  12.4%      min_depth             34,086   4.9%
  high_price_weak       52,628   7.8%      min_listing           31,202   4.5%
  min_listing           30,802   4.6%      min_sell_num          28,543   4.1%
  min_depth             27,728   4.1%      min_anomaly_buy_num   17,936   2.6%
  spread_too_wide       11,006   1.6%      spread_too_wide        5,068   0.7%
  high_price_thin_buy    3,176   0.5%      high_price_thin_buy    1,249   0.2%
  min_anomaly_buy_num    1,476   0.2%      high_price_weak        4,464   0.6%
  min_buy_num              210   0.0%      min_buy_num               49   0.0%
  thin_price_noise          11   0.0%      thin_price_noise           3   0.0%
  min_platform_sell          0     —       min_platform_sell          0     —
  implausible_30m/1h         0     —       implausible_30m/1h         0     —

放行（进入评分）：A 21,811（L0 20,987 / L1 728 / L2 81 / L3 15）
                  B 190,777（L0 184,186 / L1 6,365 / L2 220 / L3 6）
评分总数 212,588，其中 L2+ 仅 322 次 = 0.15%
```

三条结论：
1. **真正干活的是 4 道**：`min_price`（压倒性）、`min_sell_num`、`min_listing`/`min_depth`、`high_price_weak`。设计上的"七道闸"实际是**一个主闸 + 三个副闸 + 一把保险丝**。
2. **保险丝（合理但从未验证）**：`min_platform_sell`、`implausible_30m`、`implausible_1h`、`thin_price_noise`、`min_buy_num` 全周期近乎 0 命中。这不算错——它们是数据故障/极端噪声护栏，本来就该长年不动；但意味着**它们的阈值从未被真实数据检验过**，且 `thin_price_noise`=10% 面对实测 |30m| p99≈1.1%（§5 探针）基本永不触发。
3. **预算浪费**：`min_price` 占拦截 69%~82% ⇒ 榜单深翻抓回来的绝大多数是 ¥5 以下的印花/胶囊/涂鸦。**优化点不在评分，而在扫描选品**：先按价格带取榜，而不是取全价格榜再逐条丢掉。

### 3.5 其它口径缺陷（保持不变，已复核）

1. `price_change_1d` 列实际存 **7 日**涨跌（`runner.py:703`），`commands.py:246-247` 又当"近 1 日"喂给量价解算（`bot.py:914` 已修）→ 价格窗口 7 天 vs 盘口窗口 30 分钟，**横向尺度错配**。
2. 周期窗口容差=窗口一半（`cycle.py:80`），`phase_window_minutes=120` 时实际比 1~3 小时；`min_points` 放宽到 2（`engine.py:536`、`bot.py:969`）→ **两点即可判"建仓"**。
3. **"建仓"不校验 30 日位置**（`cycle.py:202-206`）：只要求 1h 横盘，高位回抽 2% 也算建仓，与文案承诺（`alert.py:194`"T+7 唯一低价进场窗口"）不符。
4. `digest_label` 用 `history[-1]` 而非当前快照（`cycle.py:237-238`），与 `detect_phase` 口径不一致。
5. 事件表混用两套等级：339 条 `L2/L3/L4` + 139 条 `mid/high/strong`（`price=0`）；`scan/restock/fake` score=0 且无雷达字段（`commands.py:190`）。
6. **模型自相矛盾**：`cycle.py:20` 自己写明"求购单几乎零成本，单点增长不可信"，而占推送 41% 的 `accum/launch` 判据核心正是**求购净增 + 求购价上移**。
7. 推荐策略：实时路径 `low_7d` 与 `dip_7d` 同一分支（`recommender.py:259-262`）；`liquid` 候选池是**价格榜前 3 页**（`recommender.py:275`）；`_liquidity` 把项目自认脏数据的 `steam_buy_num` 计入（`recommender.py:299-305`，`cycle.py:14` 明确剔除）。QQ 端 `/推荐` 走的正是 `recommend_realtime`（`bot.py:1411/1445`、`agent.py:483`），所以这些都会直接影响用户。

## §4 回测（v2：加入每日 Rank IC 与价格分层）

**方法**：事件取 `anomaly_events` 中有价者 339 条 / 254 品（2026-08-31 ~ 09-24）；基准价=事件落库价，前瞻价取 `item_listing_history` 最近点（容差=窗口 25%）；对照=**同一批品在非事件时刻**同口径；配对=事件收益 − 该品自身对照均值；另加**每日横截面 Rank IC**。

```
市场背景：随机 400 品买入持有 中位 -2.03%，上涨占比 20.5%（下跌区间）
对照(同样品/非事件) +24h -0.33%  +72h -1.42%  +168h -3.46%

【A】配对超额（事件 − 该品自身对照）
  ALL       +0.00% / -0.45% / +0.18%    跑赢自身对照 49.6% / 44.4% / 51.8%
  accum     +0.12% / -0.59% / -0.25%    52.2% / 39.2% / 45.0%   (n=46/51/40)
  launch    -0.20% / -2.13% / +2.22%    43.6% / 38.7% / 55.0%   (n=39/31/20)
  surge     -0.81% / -1.50% / -3.23%    30.8% / 25.0% /  9.1%   (n=13/12/11)
  normal    +0.05% / +0.14% / +0.42%    52.3% / 52.3% / 57.1%   (n=44/44/42)

【B】每日横截面 Rank IC（当日≥5条事件的日数）
  +24h  IC均值 +0.122  IC中位 +0.169  正IC天数 69%  (13 天)
  +72h  IC均值 +0.040  IC中位 +0.102  正IC天数 58%  (12 天)
  +168h IC均值 -0.001  IC中位 +0.039  正IC天数 50%  (10 天)

【C】价格分层 +168h（检验"低价=噪声"）
  ¥<50        n=101  中位 -7.93%  胜率 21.8%
  ¥50-300     n= 31  中位 -8.98%  胜率 12.9%
  ¥300-5000   n= 19  中位 -7.86%  胜率 21.1%
  ¥>=5000     n= 72  中位 -2.44%  胜率 26.4%

【D】类型 × 价格带 +168h（同价格带内比较，剥离价格 beta）
  accum    cheap(52) -9.26%  |  pricey(9)  -4.94%
  launch   cheap(28) -11.69% |  pricey(6)  -8.15%
  surge    cheap(3)  -3.43%  |  pricey(17) -3.23%（胜率 5.9%）
  normal   cheap(41) -2.99%  |  pricey(49) -1.04%（胜率 34.7%）
```

**怎么读：**
- **[A] 超额≈0**：全事件相对自身对照没有可测的边际；`accum`/`launch`/`surge` 的点估计为负，但**未达显著**（见 §0 声明）。
- **[B] 是本版新增、也是对 v1 的纠正**：评分在 **24 小时横截面上是弱正向排序的**（IC≈+0.12），到 7 天衰减为 0。所以不能说"分数没用"——更准确的判断是：**它有点短期排序能力，但推送给用户的叙事（T+7 持有）与它真正有效的时间尺度（1 天）不匹配**。
- **[C] 证伪了"低价=更差的信号"**：中价带与低价带 7 天表现一样差，唯一明显较好的是 ¥≥5000（-2.44%），而那正是被 `high_price_*` 三重闸门卡得最死的价格带——**恰好说明闸门在高价带是有效的**。
- **[D] 是最值得警惕的一条**：在**同一价格带内**，`accum`/`launch` 一致劣于无形态的 `normal`（低价带 -9.3%/-11.7% vs -3.0%；高价带 -4.9%/-8.2% vs -1.0%）。这剥离了价格 beta，指向**周期形态判据本身可能无效或方向有误**（与 §3.5 第 2、3 条的"两点判建仓、不校验位置"互相印证）。
- **局限**：27 天 / 单一熊市 / 要价口径 / 品必须仍在池内才有前瞻价（生存者过滤）/ 配对子样本偏向老品。

## §5 总体裁定（修正）

| 层面 | 裁定 |
|---|---|
| 作为**行情播报/观察工具** | **基本合理**：口径诚实、盘口/位置/趋势直觉方向对、冷却去重与闸门体系有工程价值，且引擎层筛选严格（评分中仅 0.15% 到 L2+）。 |
| 作为**异动发现系统** | **部分不合理**：两维评分失真（`order_ratio` 退化且反向、`spread` 方向盲）；价格缺少绝对金额下限；求购深度有旁路；周期形态在同一价格带内跑输无形态事件。 |
| 作为**倒货/交易决策依据** | **不合理**：没有手续费、提现费、7 天冷却；跨平台价差**数据拿得到却没用**（`client.py` 有 yyyp/steam 价，库表只存 BUFF 价）。名字叫「倒货波」，模型里没有任何一处算过倒货净利。 |
| 市场规律本身 | 市场**有效但粗糙**：价差中位 7% ≈ 覆盖双边手续费，7 天冷却消灭日内套利，真正的价差在**跨平台**与**时间（T+7）**两个维度。机器人押在最难赚钱的维度（**单平台、日内、要价动量**）。 |

## §6 改进建议（按性价比排序，已按复核结果修订）

**P0 — 口径与真伪**
1. 文案层把"最低在售价"明确标为**要价**；用真实成交做校准前，先确认 **SteamDT 单品 K 线的价格基准是 Steam 还是国内平台**（若是 Steam 美元价，需汇率口径，不能直接与 BUFF 人民币比）。
2. 修 `price_change_1d` 语义（`runner.py:703` 存的是 `rate_7`），让量价解算与盘口同尺度。
3. 给 7d/30d 基线加合理性闸（已实测出现 ¥20 品 `7d +665%`、`30m +102%` 进 L3）。
4. **补落库并利用跨平台价格**：详情接口已有 `yyyp_sell_price`/`steam_sell_price`，`item_multi_snapshot` 加两列即可开始积累跨平台价差历史——这是"倒货"真正的主赛道。

**P1 — 标定（用分布，不用拍脑袋）**
5. `order_ratio`：**直接删掉这一维并把 5 分转给别处**，或改为"求购/在售比的分位"。注意：删掉会使所有分数下降约 4.6 分，**必须同步重标定 L2/L3/L4 与升池线**。
6. `spread`：改为**有符号**；"价差扩大"只作为风控提示，不参与异动加分；禁用"百分比之百分比"。
7. **给价格加绝对金额下限**（与盘口数量的三重判定对称）：例如 `max(¥2, 0.5%)`，同时解决低价品触发过密与"340% 价差"这类尺度假信号。**不建议按价格带一刀切禁推低价品**（数据不支持"低价=劣质信号"）。
8. **扫描选品优化**：`min_price` 一道闸吃掉 69%~82% 的拦截量 ⇒ 改为按价格带取榜，能省掉七到八成无效评估与限流预算。
9. **新增"出手成本"闸**（替代 v1 的"净利闸"，更落地）：推送文案里给出 `售价 − 求购价`（立即出手的价差成本）与"扣双边手续费+提现后的净额"，低于阈值不推或降级为观察。当前文案没有任何成本概念。

**P2 — 验证闭环（最重要）**
10. 落库**事件 → T+1d/3d/7d 收益**（同时记录要价与求购价，以区分"要价假信号"与真实移动），并落库**每日 Rank IC**；本次的 `backtest_signals.py` 可直接改成调度任务。
11. **用 §4[D] 做专项复盘**：`accum`/`launch` 在同一价格带内跑输 `normal`。**但在闭环跑满 3 个月之前不要改推送行为**——当前样本量不足以支撑行为变更，只足以支撑"进入观察名单 + 加强记录"。
12. 阈值改按**分位 + 绝对值双条件**（纯分位会在死市里为凑满 top 1% 而推送垃圾）。

**P3 — 工程与产品**
13. 推荐策略：`low_7d`/`dip_7d` 实时路径去重（`recommender.py:259-262`）；`liquid` 候选池不要用价格榜前 300；`_liquidity` 剔除 `steam_buy_num`（`recommender.py:299-305`）。
14. 事件表等级统一（`L2/L3/L4` vs `mid/high/strong`），`scan/restock/fake` 分表或加来源列。
15. 清理从未被真实数据检验过的"保险丝"阈值：`thin_price_noise=10%` 对实测 |30m| p99≈1.1% 永不触发，应下调或改成分位；`min_platform_sell` 在扫描前置 400 之下事实上是死代码，建议删除以免误以为还有一道防线。
